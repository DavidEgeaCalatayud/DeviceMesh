# V1.3 — Distributed Probes and Service Incidents

DeviceMesh V1.3 separates a synthetic monitor definition from the vantage points that execute it. A service can now be observed from multiple locations while the existing backend-local worker remains available as a fallback.

## Architecture

```text
                         DeviceMesh API
                              |
                monitor / assignment scheduler
                              |
             +----------------+----------------+
             |                |                |
             v                v                v
        Probe Murcia     Probe Madrid      Probe Cloud
             |                |                |
             +----------+-----+-----+----------+
                        |           |
                     Service A   Service B
```

Each remote probe has an identity, location, capability list and last-seen timestamp. Each `(monitor, probe)` assignment owns an independent `next_run_at`, so several probes can execute the same monitor during the same monitoring interval.

The original backend worker still uses the monitor-level `next_run_at`. It suppresses local execution while at least one enabled assignment points to a recently alive remote probe. If every assigned remote probe becomes stale, local execution resumes automatically.

## Probe registration and credentials

Probes are created from Operator Console or the operator API. Registration returns a random bearer token once. DeviceMesh persists only the SHA-256 digest of that token.

The token must be stored on the probe host as a secret:

```bash
export DEVICEMESH_SERVER_URL=https://devicemesh.example.com
export DEVICEMESH_PROBE_TOKEN='<one-time-token>'
export DEVICEMESH_PROBE_POLL_SECONDS=5
python -m devicemesh_probe --synthetic
```

For a one-cycle validation:

```bash
python -m devicemesh_probe --synthetic --once
```

The same `agents/probe` executable still supports bounded LAN discovery. Discovery continues to require an explicit `DEVICEMESH_PROBE_SCOPES` allowlist and `--scope`; synthetic-only mode does not require a discovery CIDR.

## Work leasing

A remote probe performs the following loop:

1. `POST /api/v1/probes/heartbeat`
2. `GET /api/v1/probes/work`
3. execute each leased HTTP/TCP check
4. `POST /api/v1/probes/results`

Every leased check has a `workId` and lease expiry. Submitted results are idempotent by `workId`, so retrying a result after a transient network failure does not create a second synthetic sample.

## Network boundary

Distributed HTTP/TCP execution applies the same defensive boundary as backend-local synthetic monitoring:

- loopback destinations are rejected;
- link-local destinations are rejected;
- multicast, unspecified and reserved addresses are rejected;
- HTTP follows no redirects;
- synthetic HTTP supports `GET` and `HEAD` only through monitor definitions;
- timeouts remain bounded by the monitor definition.

ICMP is represented in the capability/model contract but remains explicitly `unsupported` in the normal unprivileged probe runtime. DeviceMesh does not silently elevate probe privileges to enable raw ICMP.

## Multi-probe consensus

For every monitor, DeviceMesh selects the most recent result from each probe inside a freshness window of:

```text
max(180 seconds, monitor interval * 3)
```

The resulting classification is:

| Probe state | Classification | Meaning |
| --- | --- | --- |
| no recent observations | `insufficient_data` | no reliable distributed conclusion |
| all recent probes UP | `healthy` | service observed healthy from every vantage point |
| all recent probes DOWN | `global_outage` | probable service-wide outage |
| some UP, some DOWN | `regional_degradation` | probable regional/network-path degradation |

Examples:

```text
Murcia  DOWN
Madrid  DOWN
Cloud   DOWN
=> global_outage
```

```text
Murcia  DOWN
Madrid  UP
Cloud   UP
=> regional_degradation
```

This is a classification of DeviceMesh observations, not proof of the underlying root cause. Routing, DNS, firewall policy, ISP failures and probe-host failures can still affect a vantage point.

## Service incident lifecycle

A failed individual check is not an incident. Every synthetic monitor has two thresholds:

- `failureThreshold` — default `3`;
- `recoveryThreshold` — default `2`.

An unhealthy consensus (`global_outage` or `regional_degradation`) increments the persistent failure streak. Once it reaches `failureThreshold`, DeviceMesh opens a service incident. A healthy consensus resets failure streak and increments recovery streak. An open incident resolves when recovery streak reaches `recoveryThreshold`.

### Important V1.3 semantic detail

Thresholds count **consecutive result observations that produce a consensus evaluation**. They are not synchronized "rounds" waiting for every assigned probe to submit exactly once. This keeps scheduling asynchronous and failure-tolerant, but operators should interpret a threshold as observation hysteresis rather than an exact N-round quorum.

An open incident is classified as:

- `service_outage` when all recent vantage points fail;
- `regional_path` when some vantage points fail while others remain healthy.

If an incident remains open, its classification can change as distributed evidence changes.

## Correlation context

At incident-open time DeviceMesh snapshots two useful pieces of context:

- whether an applicable maintenance window was active;
- whether the device associated with the synthetic monitor was currently observed offline.

These flags support diagnosis without merging host availability and service availability into one metric. A host can be online while its service is down, and a service can appear unavailable from one region while the host and other regions remain healthy.

## Incident history and MTTR

`GET /api/v1/synthetic-monitors/{monitorId}/incidents` returns current/open state plus recent incident history. Resolved incident durations are used to calculate `meanRecoverySeconds`, the current V1.3 MTTR-style summary for that monitor.

The history preserves:

- opened/resolved timestamps;
- incident classification;
- failure/recovery thresholds used at the time;
- failing and total probe counts;
- maintenance-at-open context;
- host-offline-at-open context.

## Operator API

Operator endpoints require the existing operator bearer token.

```text
POST  /api/v1/operator/synthetic-probes
GET   /api/v1/operator/synthetic-probes
PATCH /api/v1/operator/synthetic-probes/{probeId}/state
GET   /api/v1/operator/synthetic-probe-assignments
PUT   /api/v1/operator/synthetic-monitors/{monitorId}/probes/{probeId}
PATCH /api/v1/operator/synthetic-monitors/{monitorId}/probes/{probeId}
```

Public/read-only service-observation endpoints:

```text
GET /api/v1/synthetic-monitors/{monitorId}/consensus
GET /api/v1/synthetic-monitors/{monitorId}/incidents
```

Probe endpoints use the probe bearer credential:

```text
POST /api/v1/probes/heartbeat
GET  /api/v1/probes/work
POST /api/v1/probes/results
```

## Recommended deployment

For meaningful outage classification, run probes in failure domains that do not share the same network path. For example:

```text
Murcia office / home network
Madrid VPS or office
Cloud region outside the local ISP
```

Three processes on the same machine provide independent probe identities but not independent external availability evidence.

## Current limitations

- ICMP requires a future explicitly privileged probe mode or narrowly scoped OS capability.
- Probe tokens can be disabled by disabling their probe, but V1.3 does not yet rotate a probe credential in place.
- Consensus uses latest-recent observations and does not implement quorum weighting.
- Incident hysteresis is observation-based rather than synchronized-round based.
- V1.3 classifies evidence but does not perform traceroute/BGP/DNS root-cause analysis.

These boundaries are intentional. They keep the V1.3 control plane small, auditable and backward-compatible while establishing the primitives needed for later SRE/NMS features.
